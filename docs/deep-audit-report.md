## 第 0 章 本次核查的四个结论（先看这个）

### 结论 1 ✅ 「节能不牺牲舒适度」这句话已经错了，而且已被撤回

README 旧版宣称"证明节能不是靠牺牲舒适度"。实测：**baseline 41.7% → saving 20.6%**（IPMVP 原生口径），
节能策略**把舒适带内的时长砍掉了一半**。

成因不是指标算错，是指标**clamp 之后失去分辨率**：`evaluate_comfort` 的温度项在带外被压到 0，
湿度项（~0.956）扛起全部分数 ⇒ 两种模式都显示 ~0.49，**掩盖了真实差异**。

**这不是新发现，仓库已自行修正**（`cb2124b` / `7ac8e99`，README:144-151 已写明撤回）。
本文把它记为"已确认并已闭环"，不再列为缺口。

### 结论 2 ✅ 物理层有一个必须对外声明的硬限制

`τ = C_AIR/(U_WALL·A_WALL) = 25000/1800 ≈ 13.9 s`，而步长 `dt = 300 s`：

```
θ = exp(−dt/τ) = exp(−21.6) = 4.16e-10
```

**每个时间步直接落在该步的稳态上** —— 房间没有热惯性。后果：

- 任何依赖"**什么时候**用电"的策略（含 07–09 预冷）在当前模型里**原理上无法体现**；
- 17.6% 这个节能率反映的是**逐步决策**，不是**调度策略**。

README:153-162 已如实声明 ✅。**参数是故意不改的**，因为重新标定需要实测数据（见第 5 章）。

### 结论 3 ✅ 根因是 `U_WALL=12.0 / A_WALL=150.0` 高了 10–20 倍，不是指标

同类单房间的 UA 真实量级约 50–150 W/K，仓库取 **1800 W/K**。放大 10–20 倍 ⇒ 传热负荷巨大 ⇒
需要约 8000 W 制冷设备，而 `Q_AC_MAX × COP = 3500 × 3.0 = 10500 W` 冷量**不够**（缺口 89%–127%，见 1.3）。

**"设备欠配"正在意外地抑制一个坏控制律**（见 1.5）—— 这是本次核查最硬的发现。

### 结论 4 ✅ 我上一轮"换 PMV/PPD"的建议方向是错的

- PMV 需 6 项输入，我们缺 `tr` / `vr` / `met` / `clo` **四项** ⇒ 用它就必须伪造 4 个数；
- 自适应舒适度 `adaptive_en`（EN 16798-1）**只需 `tdb` + 一个可算的滑动平均温度**；
- 仓库已改用 **IPMVP 原生"带内时间占比"**（`cb2124b`），口径更简单且可与文献比较。

⇒ **正确方向不是引入 PMV 依赖，而是保持"带内占比"这个简单口径。** 详见 2.1。

## 第 1 章 舒适度 49.3% 的根因深挖

> 本章所有数字来自 `energy_system/` 的真实代码路径与 `python -m energy_system.simulation.compare`。
> 分析基线 `fee433d`；当前 `7ac8e99` 中 `settings.py` / `thermal_model.py` 参数未变，
> `comfort_eval.py` 新增了 `time_in_band_share()` 但未改 `calc_TCI`，故本章结论仍成立。

### 1.1 「49.3%」里温度只占 22.5%

`comfort_eval.py:73`：

```python
comfort = (tw * tci + hw * h_score) / (tw + hw)     # 默认 tw=0.6, hw=0.4
```

实测拆解（3 天 / seed=42）：

| 分项 | 值 | 占 comfort 的比例 |
|---|---|---|
| `0.6 × mean(TCI)` | **0.111** | 22.5% |
| `0.4 × mean(湿度分)` | **0.382** | 77.5% |
| 合计 | 0.4935 | 100% |

**湿度项几乎满分** —— 湿度生成器 3 天均值 61.5%，`calc_humidity_score`（`comfort_eval.py:28-46`）
给 0.9561。落在 40–60% 区间的样本只有 39.0%，但衰减是 `1 − dev^1.5`，不惩罚 ⇒ 均值仍高。

⇒ **"舒适度 49.3%"这个数字，超过四分之三来自一个基本没扣分的湿度项。**
汇报它时不带拆解会误导 —— 这正是 README 现在改成同时报"带内占比"的原因。

### 1.2 TCI 有一半时间是饱和的 0

`comfort_eval.py:24-25`：

```python
tci = 1.0 - abs(effective_temp - opt_temp) / delta_allow   # opt=26, delta=2
return max(0.0, min(1.0, tci))
```

实测（3 天 / seed=42，864 个样本）：

| 现象 | 数值 |
|---|---|
| `TCI == 0`（饱和） | **453 / 864 = 52.4%** |
| `TCI == 1`（饱和） | 0 / 864 = 0.0% |
| `T_in` 最大值 | **37.47 °C** |
| `T_in` 均值 / 最小值 | 26.48 / 21.36 °C |

⇒ **29 °C 与 40 °C 同为 0 分。** 指标在最需要分辨率的过热区间完全没有分辨率。

另一个方向性问题（这是仓库自己发现的）：

```
calc_TCI(24.0, 50) = 0.00     ← 24 °C 落在 26±2 带外
calc_TCI(26.0, 50) = 1.00
控制器 t_set = 24.0 °C（controller.py:26）
```

**项目在自己追求的温度上给 0 分。**

⚠️ **一个后来才被纠正的误解**：早期分析（含我第一版）认为"24 °C 得 0 分"是核心问题。
`docs/setpoint-study.md` 用扫描证明**不是**：`controller.py:81` 的 `SCHEDULE` 是**分时段**的，
白天 24 °C、夜间 26–28 °C；`controller.py:26` 的 `t_set=24.0` 只是字段初值，运行时不生效。
⇒ **但结论仍然成立** —— 只是机理是"整条 schedule 都落在 26±2 的带外或边界"，不是"单点 24"。

### 1.3 物理不可行：满功率制冷也够不到舒适上限

代入 `settings.py` 实测值：

```
UA      = U_WALL × A_WALL = 12.0 × 150.0 = 1800 W/K
C_AIR   = 25000 J/K
τ       = C/UA = 13.89 s ;  dt/τ = 21.6 ;  θ = 4.16e-10
Q_AC_MAX = 3500 W(电) × COP_COOLING 3.0 = 10500 W(冷量)
Q_solar_max = α 0.7 × I × A_win 5.0 = 3.5·I   (I=1000 → 3500 W)
```

因 `θ ≈ 0`，"满功率制冷稳态温度"可直接闭式求解
（`thermal_model.py:51-55` 的精确解：`T_inf = T_out + Q_const/UA`）：

| 场景（T_out = 35 °C，即生成器峰值） | 满制冷稳态 T | vs 舒适上限 28 °C |
|---|---|---|
| 夜间（`Q_solar=0`, `Q_int=50 W`） | **29.19 °C** | ❌ 不可达 |
| 白天峰值（`I=1000`, `Q_int=550 W`） | **31.42 °C** | ❌ 不可达 |

维持 24 °C 所需的冷量 vs 设备能力：

| 场景 | 需要冷量 | 设备能给 | 缺口 |
|---|---|---|---|
| 夜间 | 19 850 W | 10 500 W | **−9 350 W（89%）** |
| 白天峰值 | 23 850 W | 10 500 W | **−13 350 W（127%）** |

⇒ 需额定功率 6 617–7 950 W，现有 3 500 W。

实测佐证：`T_in > 28 °C` 的样本占 **34.8%**（301/864）。
**这 34.8% 是设备物理上做不到，不是控制策略差。**

### 1.4 换指标不能救它 —— 而且会让数字更难看

同一条 T 序列（3 天 / seed=42），五种口径重算：

| 口径 | 值 | 备注 |
|---|---|---|
| 现口径 `0.6·TCI + 0.4·Hum` | **0.4935** | 被 clamp + 高湿度分掩盖 |
| 只 TCI | **0.1851** | 真实温度表现 |
| 只湿度 | 0.9561 | 几乎满分 |
| **IPMVP 带内占比 [23, 26]** | **0.4167** | 严格口径 |
| EN 16798 夏季带内占比 [25.4, 30.4] | 0.5787 | 宽松口径 |
| 项目自带带内占比 [24, 28] | 0.4711 | 仓库 `settings.py:12-13` |

⇒ **换成 IPMVP 严格口径，数字从 49.3% 掉到 41.7%。**
换指标的价值是"**变得可与文献比较**"，**不是"让数字变好看"**。
必须提前接受"数字会一路下滑"这个事实，否则中途会误判为"改错了"而回滚。

### 1.5 最硬的发现：设备欠配正在抑制一个无阻尼控制律

`controller.py:230-231`：

```python
power_ratio = min(1.0, delta / 3.0)          # 比例带 3.0 K
power_ac = settings.Q_AC_MAX * max(0.3, power_ratio)   # 30% 功率地板
```

**问题 ①：在 `θ≈0` 的世界里，比例带毫无意义。**
实测"每 350 W 对应多少稳态温差"（T_out=23 夜间）：

| `P_ac` (W) | `Q_ac` (W) | 稳态 T |
|---|---|---|
| 0 | 0 | 23.03 |
| 350 | −1050 | 22.44 |
| 1050（=30% 地板） | −3150 | **21.28** |
| 3500 | −10500 | 17.19 |

⇒ 每 350 W ≈ 0.58 K。**"最小功率"等价于"一开机就过冲到 21.3 °C 稳态"。**
控制器实际是 bang-bang，比例带 3.0 K 从未真正起作用。

**问题 ②：设备一旦够大，无阻尼振荡立刻暴露。**
只把 `Q_AC_MAX` 提到 8000 W、其他不变（夜间 T_out=23，设定 24）：

| step | T (°C) | `P_ac` | 动作 |
|---|---|---|---|
| 0 | 23.03 | 0 | 停机 |
| 1 | **35.47** | 8000 | 制热 |
| 2 | **9.69** | 8000 | 制冷 |
| 3 | 35.47 | 8000 | 制热 |
| 4 | 9.69 | 8000 | 制冷 |

**完美周期振荡，幅度 ±13 K。**

⇒ **当前"还能跑"是因为功率不够大打不到过冲，不是因为控制律对。**

**反事实矩阵**（同一轨迹，只改一项；`[24,28]` 达标率）：

| 场景 | T mean | T max | 达标率 | 抖动 >3K |
|---|---|---|---|---|
| 现状 | 27.49 | 37.47 | **42.9%** | 79.6% |
| 只加设备 → 8000 W | 25.51 | 44.47 | **16.3%** ↓↓ | 94.3% |
| 只把 UA 改到 100 | 24.55 | **103.92** | **6.7%** ↓↓↓ | 100% |
| UA + C 都改真值 | 28.44 | 44.88 | 6.5% ↓↓ | 62.6% |

**加设备反而让达标率从 42.9% 掉到 16.3%；改物理参数让温度冲到 104 °C。**

⇒ **三项必须一起改。任何单独改动都会让数字更难看 —— 这就是过去每轮"改了没效果"的根因。**

### 1.6 一个重要的量化前提：C 在当前参数下不可辨识

`scripts/identify_rc.py` 的共线守卫（`:102`，`|rho| > 0.98` 拒答）是正确的，
但**用当前演示参数永远测不出 C**：

```
dt/τ = 21.6  ⇒  θ = exp(−21.6) = 4e-10
```

⇒ ZOH 回归的正规矩阵**严格奇异，`corr = 1.0000000000`**。
温度在每个采样间隔内已到稳态，**C 不含任何动力学信息**。任何求解器都救不了。

⇒ 重新标定前必须先改物理参数（让 τ 进入 0.5–2 h），否则拟合结果是伪数。
仓库已在 README:159-162 写明这一点 ✅，并在 `identify_rc.py:115` 加了**正性守卫**（UA/C 非正则拒答）。

### 2.9 rcmodel —— 不引入（理由已改写，见下）

| 维度 | rcmodel | 我们的 `identify_rc.py` |
|---|---|---|
| 代码量 | 15 文件 / **3273 行** | 1 文件 / **244 行** |
| 依赖 | `torch` `torchdiffeq` `xitorch` `ray[rllib]` `gymnasium` | **零** |
| 求解 | 神经 ODE（`torchdiffeq.odeint` + rk4，`rc_model.py:100`） | 手写 2×2 正规方程闭式解（`:60-82`） |
| 待拟合量 | **9 参数 + loads 矩阵**（`helper_functions.py:103` 断言 `len==9`） | **2 个标量** |
| 优化目标 | `Adam(maximize=True)`（`optimise_models.py:181`）—— **最大化 reward** | 最小化拟合残差 |
| 范式 | **PPO + 物理/策略双循环交替**（`cyclic_manager.py:56-100`） | 无需迭代 |
| 可复现性 | PPO 随机 ⇒ **同输入不同结果** | `R²=1.0000` 精确复原 |

**三条不引入的理由（都可被追问）**：
1. **它优化的是 RL reward 而非拟合残差**（`optimise_models.py:181` `maximize=True`）⇒ 用 RL 解一个 2×2 线性方程组，
   不给你想要的那个量的语义；
2. **PPO 路径不确定** ⇒ 无法满足本项目 **golden 断言式的可复现标定**（`test_simulation_baseline.py`）；
3. **数据形态不匹配**：它要连续轨迹（ODE 积分），我们手上是离散 CSV。

**它真正值得带走的一条已被吸收**：`helper_functions.py:105` 用 `torch.logit` 把参数约束在正数域
⇒ 我们的等价实现是 `identify_rc.py:115` **直接拒答非正的 UA/C**（2 标量场景下更简单也更严格）。

**结构性提示（方向对，但现在不该做）**：`rc_model.py:105` 注释 "first two columns are external envelope nodes"
⇒ 3R2C 把**墙体热容**作为独立节点，我们只有空气热容 ⇒ 这正是"空调一动温度就立刻到位"的根源。
但升到 2 状态模型需要更多数据点才能辨识（多出的节点参数无法辨识时就是新的共线性），
而我们连 1R1C 的实测数据都还没采到。

## 第 5 章 可执行结论与顺序

### 5.1 三件必须一起做的事（有严格顺序依赖）

| # | 改什么 | 为什么必须在这个位置 | 验收指标 |
|---|---|---|---|
| **1** | `settings.py`：`U_WALL` 12→约 1.0（使 **UA ≈ 150 W/K**）、`C_AIR` 2.5e4→约 **3.6e5**（τ≈1 h） | 不改则后面全白做。**UA 与 C 必须同时改**，只改一个会失控（见 1.5 场景 3：T 冲到 104 °C） | `τ = C/UA ∈ [0.5, 2] h`；单步 `θ = exp(−dt/τ) > 0.9` |
| **2** | 控制律改成**稳态前馈 + 小比例修正**，去掉 30% 功率地板 | 现状是 bang-bang，任何"设备够用"的改动都会引爆 ±13 K 振荡（见 1.5 问题 ②） | 相邻步 `\|ΔT\| > 3 K` 的比例 **< 5%**；`T_in ∈ [21,29]` 全程 |
| **3** | 指标保持 **IPMVP 带内占比 [23,26]**（仓库已改，`cb2124b`） | 只有 1、2 做完才有意义 | 带内占比 **> 70%**；达不到就如实报告物理上限 |

**顺序不能颠倒：1 → 2 → 3。** 理由：3 的输出是 1、2 的度量。先改 3 只会得到一个"更难看但没意义"的数字。

### 5.2 前置件（决定 #1 能否做）

| A | **加一个室外温度传感器**（DHT22）或改用气象再分析数据 | 1 个传感器 + 3 天记录 | ⚠️ **绝不要用仿真的天气生成器充当 `T_out`** —— 那是用仿真拟合仿真，结论无效 |
