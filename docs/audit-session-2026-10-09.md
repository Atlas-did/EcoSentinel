### 3.4 §6.2 的技术判断 — ✅ **在引擎原理上成立，值得留存**

纪要对 `__has_include` 死锁的分析：arduino-cli 只依据**预处理输出中真正出现的 `#include`** 去解析/编译库；库缺失时条件为假可理解，但库**已安装**时第一遍求值仍为假 → `#include` 不出现 → 库永不被解析。并指出用 `-I` 强行可见会跳过库解析，导致 `undefined reference to 'DHT::readTemperature'`。

这一判断与 arduino-cli 的 `ResolveLibrary(...)` 工作方式相符，且**同类隐患在仓库中确有 5 处**（`config.h:19/26/33/41/48`，DHT / SGP30 / TFT / INA219 / TOUCH），所以纪要关于"将来接这几个传感器会遇到完全相同的坑"的预警**有实际价值**。

**但请注意**：该结论在本机**无法验证**（无 arduino-cli、无 ESP32 核心、无硬件）。纪要在这一点上是可信的**外部经验**，不是本仓库可复现的证据。

### 3.10 §4.3「必须加 CDCOnBoot=cdc」— ✅ 有价值，且暴露 `AGENTS.md` 的一处不足

纪要 §4.3 指出：按 `AGENTS.md` §4 的原始命令 `--fqbn esp32:esp32:esp32s3` 编译烧录后**串口完全无输出**，因为 ESP32-S3 用内置 USB-Serial/JTAG，默认 `CDCOnBoot=disabled` 会把 `Serial` 路由到 UART0（GPIO43/44）而非 USB 口。正解是加 `:CDCOnBoot=cdc`。

这是**真实且高价值的踩坑**。而对照 `AGENTS.md` §4 当前内容：

```bash
arduino-cli compile --fqbn esp32:esp32:esp32s3 firmware/esp32_s3_competition
```

——**确实缺 `CDCOnBoot=cdc`**。也就是说 `AGENTS.md` 的固件配方**对 ESP32-S3 上板是失效的**，纪要的这条发现应当回灌到 `AGENTS.md`，但**尚未回灌**。

### 4.2 🔴 引脚值没有任何自动化守卫

- `tests/unit/test_firmware_acceptance.py:116-120` 只断言 `KNOWN_KEYS` 的**键名集合**；
- `tests/contract/test_metrics_registry.py` 只用正则抓 `replySensorsJson` **函数体**内的键（`test_metrics_registry.py:80-94`，注释明确说"只看这一个函数"）。

因此 `config.h` 的引脚值、以及 `protocol.h:135` 的 `"dht"` 字段，**改了不会被任何测试拦住**。纪要 §6.4 反复强调"唯一可靠判据是布尔值"，但**"引脚配错"这个真实故障模式恰恰没有门禁**。这是仓库可加的一条低成本守卫。

### 4.3 🟡 `have_dht` 会因为"引脚配错"而**显示为 true**

`protocol.h:262` 打印的是 `HAVE_DHT`（编译期常量），**与引脚是否正确无关**。纪要 §6.2 把 `have_dht:true` 当作"修好了"的判据是对的（因为它只区分"编没编进去"），但**它不能证明 DHT 真的读得到**。真正的运行期证据是 §7.2 的 `temperature:27.30`。

若把 `have_dht` 误读为"传感器工作正常"，会重演纪要 §6.2 描述的同一类"假象"。**建议在使用该字段时明确它是编译期标志。**
