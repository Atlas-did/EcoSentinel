## 1. 这个项目到底是什么（详细解读）

### 1.1 规模与结构

不是"一个提示词"，而是**9 个子技能的技能包**（v5.1.0），根 `SKILL.md` 只是**路由表**：

| 子技能 | 作用 | 触发 |
|---|---|---|
| `patent-disclosure` | **交底书**：挖点→查新→成文→迭代（发明/实用/外观） | 直接可触发 |
| `patent-application` | **申请文件四件套**：权要/说明书/摘要/附图 | **须点名** + 须指定交底目录 |
| `patent-docket` | 案卷：交底→申请一趟串起来 | **须点名** |
| `patent-search` | CNIPA 著录检索 | 直接可触发 |
| `patent-reader` | 专利解读（公开号/PDF→笔记+图谱） | 直接可触发 |
| `patent-chart` | 权利要求对照表（claim chart / FTO 初筛） | **须点名** |
| `patent-map` | 专利地图（五种图，语义地形） | **须点名** |
| `patent-oa` | 审查意见答复 | **须点名** |
| `patent-exam-policy` | 审查政策简报 | **须点名** |

**工程量真实**：仅 `patent-disclosure` 下就有 30+ 个 `.py` 工具、20+ 个 prompt、13 个 YAML schema，配套 `tests/`（如 `test_cnipa_epub_crawler.py` 20KB、`test_formula_eval.py`）。这不是玩具。

### 1.2 工作流（以发明交底为例，Step 1–8）

```
Step 1  intake.md          收敛类型/联系人（缺可推断并注明假设）
Step 2  project_scan.md    按优先级扫材料（专利文档>设计文档>核心代码>系统设计）
                            └ 遇 .docx/.pptx/.pdf 必须转 md 再读
                            └ 遇 .tex 走 tex_scan.md（公式以源码为准）
Step 3-4 invention/        列 3–5 个候选专利点 → 融合选型（方法+系统）
Step 5  prior_art_search   轻量查新：3–4 个手段短语 × 公布站，LLM 摘要精排
Step 5.5 D1 锁定           钉一篇最接近 + 逐特征表 Fk + 三态门禁
Step 6  disclosure_preview 预览
Step 7  disclosure_builder 成文（+template_reference）
Step 8  self_check         自检（内部执行，不写入交付正文）
旁路    fence/             保护型 1+N 专利布局（首篇定稿后）
```

### 1.3 真正值钱的设计（我重点看的）

**a) 反幻觉护栏做得相当硬。** 这是我推荐它的主要理由：

- **禁止假 D1**：`patent_points_analyzer.md:31` 明写"**不要**指定不相干文献当 D1 或空喊「创新性强」"。
- **禁止编造文献凑数**：`disclosure_builder.md:27` —— 第二轮不足 4 条时如实写"近邻较少"，**禁止编造条目凑数**，且每条现有技术**必须给经核验的公开源 URL**（"写入前验证有效""禁止虚构链接"）。
- **禁止空喊**：`fence/guardrails.md:31` 禁止"编造营收、同族、金奖、质押"。
- **门禁不过也成文，但降级**：`D1 锁定`不过时"仍成文但创造性降级"，**不停笔**——这个设计比"卡住不写"更实用。
- **抽象级证据不得当依据**：`disclosure_builder.md:116` —— 仅从 PDF 文本层抄的公式 `verified: false`，"**不得当作 Fk / 创造性依据**"。

**b) 交底书结构极贴合中国实务**（`disclosure_builder.md:23`）：

- 第五章强制分 **5.1 必要技术特征 / 5.2 优选特征**，按**删除测试**划分 —— 这直接喂给 `patent-application` 的 `claim_strategy.md:5`（"独权只取 5.1，从属树取 5.2，**不要**重新自行判断必要性"）。**交底与申请的接口是通的**。
- 3.4.1 符号与公式：先用 `formula_plan.yaml` 声明 `origin: source | agent`，跑 `check_formula_plan.py --eval` 校验；**材料没有的式子才能起草**，且起草的必须给可代入数值例。
- 框图/流程图强制 **mermaid → PNG**（`mermaid_render.py` 走 Playwright，不依赖 Node/mmdc/外网 PlantUML），且**步骤号必须写进可见标签**。

**c) 脱敏有自己的边界**（`disclosure_builder.md:102-103`）：挡住真实主体/产品名/精确数值，但**不得借脱敏把案件名称里的领域对象收成更空的上位词**。这条对生态监测这类"有具体场景"的项目很受用。

### 1.4 已知限制（必须知道）

| 限制 | 出处 | 影响 |
|---|---|---|
| **`.doc` 不支持** | `project_scan.md:106`、`docx_to_md.py:53` | 你的两份材料都中招，须先转 `.docx` |
| 依赖较重 | `requirements.txt` | `playwright`（过 WAF）、`mammoth`、`python-pptx`、`latex2mathml` |
| 查新强依赖 CNIPA 站点 | `prior_art_search.md:13` | 站点/网络问题则降级 WebSearch；本机网络需验证 |
| 环境敏感 | `requirements.txt`、`cad` 说明 | 明确警示 **Python 3.13+ 不行**（CadQuery wheel 只到 3.10–3.12）；本机是 **3.14** |
| 法律定位 | 根 `SKILL.md` description | **"不构成法律意见"**，claim chart 只是底稿 |

## 2. ⚠️ 前提纠正：你给的两份 `.doc` 是「软著」材料，不是「专利」材料

我把两份文件都完整提取了，它们属于**两个不同的知识产权体系**：

### `新系统软著采集表模板-新系统.doc` —— 软件著作权登记表

提取到的字段（共 70 段）明确是**软著**登记口径：

- 权利取得方式（原始/继承/承受/其他）、软件全称（**须以"软件/系统/平台"结尾**）、版本号
- **软件分类**（应用软件/嵌入式软件/中间件/操作系统）、开发方式（单独/合作/委托/下达任务）
- **源程序量**（源代码行数）、开发目的、面向领域
- **软件的主要功能 500–1300 字**
- 技术特点勾选：`APP / 游戏 / 教育 / 金融 / 医疗 / 地理信息 / 云计算 / 信息安全 / 大数据 / 人工智能 / VR / 5G / 小程序 / 物联网 / 智慧城市`

### `参考-软著设计说明书.doc` —— 软著设计说明书范本

结构是**三章**：第一章引言（编写目的/范围/参考文献/预期读者）、第二章系统概述（概述/运行环境）、第三章总体设计（系统目标/软件功能说明/系统设置）。

**注意：它的正文内容是"显示屏生产线品质检测系统"（6 台相机的图像检测、NG 图片、蜂鸣器报警、TXT 报告）——与 EcoSentinel 毫无关系**。文件开头已注明"**注：本文件为仅为参考文件，申请人可根据贵司软件产品的特点进行撰写**"。**它只是一份格式模板，不是内容素材。**

### 两条路的区别（这决定你该做什么）

| | **软著（你手上的两份 .doc）** | **专利（这个 skill 干的活）** |
|---|---|---|
| 保护对象 | **代码表达本身**（源代码 + 文档） | **技术方案 / 构思**（方法、系统、结构） |
| 审查 | **形式审查，不查新颖性**，基本必过 | **实质审查**，查新颖性/创造性/实用性 |
| 材料 | 源代码 60 页 + 说明书 + 登记表 | 技术交底书 → 权利要求书/说明书/摘要/附图 |
| 周期 | 通常 1–3 个月 | 发明 1.5–3 年；实用新型 6–12 个月 |
| 费用 | 低 | 较高（代理费为主） |
| 本 skill 能否直接帮 | **不能**（它是专利技能，不是软著技能） | **能，正是它的主场** |

> **所以：这两份 `.doc` 对"跑这个专利 skill"没有任何直接价值**——它们是**另一条路**的材料。它们唯一的价值是让我确认：你**同时**在考虑软著。这是好事，两条路可以并行（见 §5.3）。

**如果要做软著**：`参考-软著设计说明书.doc` 给了章节骨架，EcoSentinel 的 `README.md`/`docs/` 足以填第三章；`新系统软著采集表模板` 的字段我可以逐项填。这属于**另一项任务**，本报告只标注可行性。

## 3. EcoSentinel 能不能做专利？—— 能，且素材质量好

### 3.1 先看技能要什么

`project_scan.md:9-15` 的优先级表要的是：**算法与策略实现、业务逻辑与流程编排、数据处理与转换、规则引擎与决策逻辑、接口与集成设计、状态机与调度机制、性能优化与缓存策略**。

EcoSentinel 的 `energy_system/` **正中靶心**。

### 3.2 我判定的候选专利点（初步，**未经查新**，仅供你判断材料是否够）

> ⚠️ 以下是我的**初步识别**，**不是**查新结论，**更不是**可专利性结论。真正的判定必须走 Step 5 查新 + Step 5.5 D1 锁定。**不得**把本节当作"已经证明有创新性"。

**候选点 A：设备-围护可控性匹配判定方法（我评最高）**

依据是仓库里**未提交**的 `energy_system/config/settings.py` 新增的 `check_controllability()`：

- 用**权限比（authority ratio）**而非绝对温度做判据：`制冷权限比 = 可用冷量 / 维持目标所需冷量`，须 ∈ [1, 8]
- 明确记录"两套参数在可控性上**反向失配**"（demo UA=1800 压不住 29.2°C；realistic UA=150 过冲到 −12.7°C）
- 有**制热需求的触发条件**（只在需求 > 设备能力 5% 时才判定，否则标记"本工况未触及"）—— 这是一个**避免除零/无意义比值**的具体工程处理
- 有配套测试 `tests/unit/test_controllability.py`

**为什么看好**：这是一个**具体的、可写进权利要求的判定方法**，有明确的技术问题（选型与围护失配）、明确的手段（权限比 + 双向门槛 + 触发条件）、明确的效果（避免选型错误导致的控温失效）。符合"方法+系统"的融合方向。

**候选点 B：热惯性联合约束与参数集具名化**

依据：提交 `9d0e03c`（"具名参数集 + 热惯性联合约束门禁"）+ `94f6dcf`（"修默认参数的定义时求值坑 + 机制敏感门禁"）。

**候选点 C：稳态前馈 + 小比例修正的控制策略**

依据：提交 `3d1b986`（"稳态前馈 + 小比例修正、去掉 30% 地板"）。这是**控制器策略**类，属专利常见客体。

**候选点 D：确定性仿真回归基线 / IPMVP 配对对照**

依据：提交 `5477f50`（"baseline 侧对照矩阵 + IPMVP 配对对照"）。**注意**：这一条更接近"**测试方法**"，可专利性**明显弱于 A/B/C**，且部分可能落入"智力活动规则"。**建议不优先。**

**候选点 E（实用新型方向）：ESP32-S3 多传感器边缘节点结构**

仓库有 `firmware/esp32_s3_competition/`（继电器×4、蜂鸣器、步进电机、BH1750/SGP30/DHT22、TFT）。若你有**具体的结构改进**（如传感器布局、抗干扰、供电），可走**实用新型**（只保护形状/构造，不审创造性到发明的高度，下证快）。但**纯软件逻辑不能报实用新型**。

### 3.3 材料充足度自评

| 技能需要的 | EcoSentinel 是否有 | 说明 |
|---|---|---|
| 详细设计/方案文档 | ⚠️ **部分** | `README.md` 14KB、`docs/` 多份、`EcoSentinel_代码重构详细实施计划.md` 50KB；但 §7 明确记"docs/ 缺一份重构设计书" |
