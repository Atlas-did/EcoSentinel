# 第一部分：中国专利的"很多种形式"到底是什么

你说的"很多种形式"，在中国专利法下确实有三层分类维度。**选错类型是最常见的浪费**——下面逐个讲清。

## 1.1 三种专利类型（这是最主要的分类）

| | **发明专利** | **实用新型专利** | **外观设计专利** |
|---|---|---|---|
| **保护对象** | 产品、**方法**、系统、用途 | **只保护产品的形状、构造或其结合** | 产品的形状、图案、色彩及其结合 |
| **能否保护纯方法/算法** | ✅ **能**（这是唯一能保护方法的） | ❌ **不能** | ❌ 不能 |
| **能否保护纯软件逻辑** | ⚠️ 有条件（见 §1.2） | ❌ **完全不能** | ❌ 不能 |
| **审查方式** | **实质审查**（查新颖性/创造性/实用性） | **初步审查**（不查创造性实质） | 初步审查 |
| **授权周期** | **1.5–3 年**（可请求优先审查缩短） | **6–12 个月** | 4–8 个月 |
| **创造性要求** | 高（"突出的实质性特点"） | 较低（"实质性特点"） | 无（比的是"是否近似"） |
| **保护期限** | 20 年 | **10 年** | **15 年** |
| **官费（未减免）** | 申请费 900 + 实审费 2500 | 申请费 500 | 申请费 500 |
| **是否需要附图** | 视情况 | **必须有** | **必须有**（视图） |

### ⚠️ 对你这个项目最关键的一句话

**EcoSentinel 的算法、控制策略、AI 调度逻辑，只能走「发明专利」。**

互联网上常说的"软著 + 实用新型双报"，对**纯软件逻辑是行不通的**——实用新型明确不保护方法和软件。**只有固件的物理结构改进**（如传感器安装结构、散热结构、接口布局）才能走实用新型。

## 1.2 软件/算法能不能申请发明专利？—— 这是核心问题

**能，但有条件。** 中国专利法第 25 条把"**智力活动的规则和方法**"排除在授权范围外。纯算法、纯数学公式、纯商业规则**不能**直接授权。

**但是**：《专利审查指南》明确规定——如果一项权利要求**整体上**包含了**技术特征**、解决了**技术问题**、产生了**技术效果**，就属于可授权的客体。

**怎么判断你的软件是不是"技术方案"？** 实务上看三条：

| 判据 | 不合格（纯智力规则） | 合格（技术方案） |
|---|---|---|
| 是否与技术领域结合 | 抽象的"一种排序方法" | "一种**空调压缩机**的控制方法" |
| 是否处理技术数据 | 处理金融数据、文本语义 | 处理**温度、功率、传感器信号** |
| 是否产生技术效果 | 仅是"计算更快" | "减少压缩机启停次数""降低能耗""避免过冲" |

**对照 EcoSentinel：三条全过。**
- 它与**空调、继电器、传感器**这些物理设备结合（技术领域 ✅）
- 它处理**温度、湿度、功率**这些物理量（技术数据 ✅）
- 它产生**减少启停、降低能耗、避免温度过冲**的效果（技术效果 ✅）

**所以：EcoSentinel 具备申请发明专利的基本资格。** —— 但这只解决"**客体**"问题（能不能报），**不解决"创造性"问题**（报了能不能授权）。后者**必须查新**才能判断。

## 1.3 其他容易混淆的"形式"

| 概念 | 说明 | 与本项目关系 |
|---|---|---|
| **发明 / 实用新型 / 外观** | 三种法定专利类型 | 见 §1.1 |
| **软著** | **不是专利**！著作权的一种，只保护代码表达，不查新颖性 | 你已在做（见另一份填写稿） |
| **PCT 国际申请** | 一次申请、多国生效的通道 | 先国内后国际，现在不用考虑 |
| **优先权** | 先申请一件，12 个月内可就相同主题在别国/本国再申请 | 若想布局海外才有用 |
| **分案申请** | 一件申请中含多个发明时拆开 | 若挖出多个独立创新点可能用到 |
| **专利布局（1+N）** | 1 件核心 + N 件外围，形成保护网 | 首篇定稿后可做，见 §4 |

# 第二部分：EcoSentinel 到底有什么可申请（逐条评估）

我通读了 `energy_system/` 的核心模块。以下是**从真实代码里找到的**候选点，不是泛泛而谈。

## 候选点 A：基于"权限比"的设备-围护匹配判定方法 ⭐ 推荐度最高

**代码依据**：`energy_system/config/settings.py` 的 `check_controllability()`（**未提交**，在工作树里）

**技术问题**：空调选型与房间围护结构失配时，会导致两种失效——设备太小"压不住"（温度达不到目标），设备太大"一开就冻"（过冲到非物理温度）。传统做法凭经验估算，缺乏可断言的判据。

**技术手段**：
- 定义**制冷权限比** = 可用冷量 /（UA·(T_out峰值 − T_set) + Q_太阳 + Q_内热）
- 定义**制热权限比** = 可用热量 /（UA·(T_set − T_out谷值) + Q_内热）
- 双向门槛：比值 < 1 判"权限不足"；> 8 判"权限过剩"
- **关键创新**：制热侧只在"需求 > 设备能力 5%"时才判定，否则标记"本工况未触及"——这解决了室外温度接近设定值时**除零/无意义巨大比值**的工程问题

**技术效果**：把"选型合不合理"从经验判断变成**可计算、可断言、可在 CI 里跑的比值判据**。

**为什么推荐**：这是**结构最完整**的一条——有明确问题、明确手段、明确效果，且**有配套测试**（`tests/unit/test_controllability.py`）。最像能写成独立权利要求的一条。

**⚠️ 风险**：这属于"**参数校验/设计方法**"，可能被审查员认为偏"智力活动规则"。**对策**：权利要求里**必须绑定物理量**（房间 UA、室外温度、制冷量 W），并写明"据此选型/控制设备"的物理动作，不能写成纯公式。

## 候选点 B：热惯性联合约束的参数集校验方法

**代码依据**：`settings.py` 的 `check_parameter_set()`、`describe_parameter_set()`

**技术手段**：
- 约束写成不等式 `C/UA > dt / ln(1/0.9)`，等价于 `θ = exp(−dt/τ) > 0.9`
- 语义：**仿真步长下"一步之后模型仍保留 >90% 记忆"**，否则热模型退化为无记忆系统
- 分离"计算"与"判定"：`describe_*` 只算不抛错，`check_*` 违规才抛错（单一真相源）

**技术效果**：拦住"参数看似合理、仿真实则发散"的**无效仿真**——这在本项目里**真实发生过**（历史上 29.6%/29.8%/29.9% 的节能率就出自欧拉发散，已作废）。

**评价**：问题真实、手段具体。但**它的性质更像"仿真可信度保障"**，单独成案偏弱，**建议作为候选 A 或 C 的从属权利要求**。

## 候选点 C：AI 建议与物理执行的解耦控制方法 ⭐ 推荐度高

**代码依据**：`energy_system/ai/`（circuit_breaker / fallback_policy / response_parser）+ `core/controller.py` + `resilience/`

**技术问题**：把大模型直接接入物理控制系统有**安全风险**——模型可能幻觉、超时、返回非法指令，直接执行可能损坏设备或造成安全事故。

**技术手段**（三层）：
1. **语义隔离**：模型输出**只作为建议**，规则控制器做**最终执行决策**（"模型返回 ≠ 设备执行"）
2. **逐候选熔断**：每个候选模型独立计数，连续失败达阈值则开启熔断，开启时长**指数退避** `min(base × 2^n, max)`，配合**EMA 评分**（`circuit_breaker.py:27-83`）
3. **本地兜底**：全部候选熔断时降级到纯规则控制，闭环不中断

**技术效果**：云端不可用/模型异常时，物理控制**不中断、不误动作**。

**评价**：**这是最有"现代性"的一条**，结合了 LLM 与工业控制，且**技术效果明确**（可靠性）。`circuit_breaker.py` 的指数退避 + EMA 是有具体参数的手段。

**⚠️ 风险**：熔断器本身是**成熟技术**（微服务领域常见），单独写"用熔断器"缺乏创造性。**对策**：权利要求要落在**"对物理执行器的安全隔离"这个特定组合**上——即"建议-校验-执行"三层 + 熔断 + 物理兜底，而不是泛泛的熔断器。

## 候选点 D：分时段设定值 + 防抖状态机的节能控制方法

**代码依据**：`core/controller.py:30-75`（`HysteresisStateMachine`）、`SCHEDULE` 分段

**技术手段**：
- 分时段设定值：预冷 22°C → 工作 24°C → 夜间 28°C
- **最短运行时间 900s + 最短停机时间 600s** 的状态机，防止执行器频繁启停
- **可计数的防抖指标** `blocked_switch_requests`：把"3 天里拦下 N 次切换请求"变成**可验证的可靠性论据**

**评价**：**技术效果最实在**（减少压缩机启停 = 延长寿命 + 省电）。但**防抖/死区控制是空调领域的常规技术**，创造性风险**最高**。若要用，必须把新颖点落在**具体参数组合 + 可计数验证**上。

## 候选点 E：I2C 总线自愈与在线校正

**代码依据**：`resilience/orchestrator.py`（I2C 恢复、MCU 软复位、限流）、`core/data_acquisition.py:51-58`（INA219 台架校正系数）

**技术手段**：
- 分级自愈：I2C 异常→重初始化；MCU 无响应→软复位；复位有**每小时次数上限 + 冷却时间**（防止复位风暴）
- **危险动作故意不自动化**（如切断执行器电源需人工介入）
- 功率读数**在线比例校正**（固件未调 `setCalibration`，用实测比例在出读口补偿）

**评价**：可靠性设计扎实，但**多为工程常规手段的组合**。**建议并入其他案作为从属特征**。

## 候选点 F（实用新型方向）：ESP32-S3 边缘节点结构

若你的硬件有**具体的物理结构设计**（传感器安装位置、抗干扰屏蔽、散热、接线端子布局），可走**实用新型**。

**⚠️ 前提**：必须有**真实的、有形状构造的改进**。**纯模块堆叠（把 BH1750 和 SGP30 接在同一 I2C 总线）不具备新颖性**，不能报。

## 5.3 关于"宽限期"的重要澄清

网上常说"公开后 6 个月内仍可申请"——**这个说法对中国专利不普遍成立**。

- 中国专利法第 24 条规定的**不丧失新颖性例外**仅限三种情形：
  1. 在中国政府主办或承认的**国际展览会**上首次展出；
  2. 在规定的**学术会议或技术会议**上首次发表；
  3. 他人**未经申请人同意**而泄露。
- **自己在 GitHub 公开发布，通常不属于上述任何一种**，因此**一般不能主张宽限期**。

⚠️ 但请注意：**这是需要专业判断的法律问题**，具体适用性**必须咨询专利代理机构**，我不能替代。

## 5.5 一个务实的观察

即便已公开部分难以获得专利，**软著仍完全不受影响**（软著不查新颖性）。所以：

- **软著这条路照走**，你手上的采集表填写稿可以直接用；
- **专利这条路收紧到候选点 A**（未公开）+ 未来新增的未公开改进；
- 不要把已公开的候选 C/D 当作主打，**可作为 A 的从属特征**（从属权利要求的新颖性依附于独权）。
